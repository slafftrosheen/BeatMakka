# Issue #23 — personal records, deliberate listening and credited remix copies

Date: 2026-11-05. Base main: `ea3fb496e20ee8484e25ae0dcc9658f4261e9e85`. Scope: source implementation of the three bounded phases in [issue #23](https://github.com/slafftrosheen/BeatMakka/issues/23). Runtime acceptance and voluntary-use observation remain open; this document is not a Studio or hosted-persistence receipt.

## Player workflow

Open the existing Beat Shelf through the Roamer or CRATES. LOOPS, DRAFTS and FINISHED retain their musical types. CONTINUE resumes a Pattern/Loop or Draft Song without starting playback. Selecting a sleeve opens its title/type, original creator, collaborators, pack/mapping versions and current saved/unsaved/session-only status. Existing immutable Finished Songs still support full playback and editable copies; archives and recovery remain in Options.

The shelf reuses Sleeve Studio's waves, lantern and steps motifs and teal, coral and amber palettes. An unfinished item's personal sleeve is a normal project edit with Undo/Redo and explicit Save; it does not finish music. Choosing a sleeve for a release copies it independently. Existing approved device/sleeve artwork remains in use, with a native motif mark; no image generation, imported imagery or new asset binding was introduced. The approved style board was inspected. The requested Windows Assets directory and its usual Linux mount are unavailable on this host.

RELEASE A COPY offers Listen only or Allow remix. It captures the selected musical dependencies, cover and credits into an independently identified release v1. A later edit or personal-sleeve change cannot change that record. Releasing a Pattern/Loop or Draft Song preserves that type; it never manufactures a Finished Song. The same existing save transaction must accept a release before it appears under RELEASES. No invitation is sent automatically.

Under RELEASES, choose a same-server recipient and invite explicitly. Invitations expire after 45 seconds, carry one immutable release identity, and start no audio. Accept begins an audition of up to 15 seconds; Decline leaves the recipient's project and audio untouched. Listening offers replay, Stop, local mute and separate full Song playback. Pattern/Loop auditions are one bounded excerpt, not a newly finished Song or indefinite broadcast. Invited listeners do not need discovery unlocks just to hear an available shared sample.

Acceptance/replay is refused while personal playback/recording, a jam, a chapter performance or public listening owns audio. A recipient can explicitly stop their personal playback in the invitation panel. Record mute changes only the record's audio engine; it does not overwrite the existing global sound preference. Closing ordinary record listening retains the personal project's paused transport, selection and work. Author departure removes dependent invitations and listening sessions; recipient departure drops only their transient session.

A recipient away from the studio can choose STOP RECORD / OPEN MY WORKBENCH. This server-validated action uses their existing assigned room bay and station, checks availability, and teleports through the existing local transition. It retains the accepted record/token and paused personal transport rather than requiring another invitation. It does not award tutorial progress. An unavailable/occupied station leaves the accepted record available. Other ordinary station/session transitions retain their earlier behavior.

CREATE SEPARATE CREDITED REMIX rechecks current author permission, session token, workspace identity/revision/generation/edit version, save lock, audible content readiness and complete storage budget. It clones the release into a new owned project, retaining exact sequence events, arrangement/repeats/tempo maps, mixer routing, pad sound settings, sample IDs, pack versions and cover. The current workspace is preserved as an editable archive before activation; capacity failure changes neither workspace. The copy is UNSAVED until the recipient saves explicitly. A copied Finished Song becomes editable Draft Song material, requiring deliberate Finish later. A loop remains a loop. Repeated import requests from the same accepted session are rejected.

Listen-only releases reject remix commands on the server. Mutable permission is stored separately from the immutable record and changes only after save acknowledgement. Revocation affects future copies after acknowledgement; pending-save state is visible. It does not delete or claim to revoke existing lawful copies. A new explicit invitation can authorize a further copy; there is no global feed/search, automatic broadcasting, popularity currency or sales system.

## Data and responsibility boundaries

- `MusicAttribution` stores original creator, deduplicated contributors and an ordered release/version/creator lineage. Names come from server-authored player/jam records, never client-supplied credits. Selected joint-loop collaboration metadata and the sequence dependencies of new drafts are included, so rearranging a credited joint loop cannot remove its other author. Sixteen contributors and sixteen lineage entries are explicit limits; excess credits cause refusal rather than dropping names. Project edits, archives, saves and Finished Song capture retain this metadata.
- `SampleVersions` preserves each referenced stable sample ID with pack ID/mapping revision, including stored program mapping metadata. Unknown audio, unavailable audible references, conflicting pins or changed pack mappings are reported, never substituted. Normal new explicit pad/kit choices add current pins; a kit conflicting with a retained pin is refused. Copies do not grant discovery progression: remix import requires the recipient's own audible content access; missing/locked content leaves their work unchanged.
- `RecordRelease` captures only the selected sequence or Song dependencies and all required routing tracks/programs, including silent tracks that can affect global solo behavior. Internal sequence/part/kit names become fixed labels in the shared copy. Ordered resolved events and tempo/duration are compared before accepting a release or materialized remix; only the new project route identity changes for a remix. These guards are implemented but have not been executed in this environment.
- `RecordService` is the server authority for release saves, permissions, targeted invitations, playback and import. It accepts small identity/choice requests, never client project tables, schedules, creator IDs or arbitrary destinations. Existing command payload/rate and station ownership/proximity gates remain in force. Invitations/schedules are sent only to their recipient. Listening state is session-local.
- The existing library and focused native record panels expose these actions. The existing `SchedulePlayback` consumes the private record schedule. `AudioEngine.localMute` lets this player mute a record without writing `AudioMix.muted`; ambience/street speakers yield during accepted record listening.

Public titles use the current [Roblox text filtering process](https://create.roblox.com/docs/ui/text-filtering): server-side `TextService:FilterStringAsync()` and `GetNonChatStringForBroadcastAsync()` at release creation and again before each invitation. Failure refuses sharing. Simulated negative Studio IDs get the fixed shared title “Studio record”, never unfiltered custom text. On remix, the invitation/session's freshly filtered title replaces stored project/draft titles in the new copy; the immutable original is untouched. UTF-8 boundaries are retained when prefixing a long remix project name. Real filtering acceptance remains unobserved.

## Persistence and compatibility

Profile schema is now 4; music schema is 2. Existing profile 3/music 1 documents are validated, cloned and upgraded by adding empty `releases`, `releaseOrder` and `releaseRequests` indexes. Legacy pattern migration still runs, now targeting music 2. Existing project, archive order, read-only legacy preimages, recovery, Finished Songs, finish receipts and earned profile progress remain intact. Unsupported future or malformed roots fail closed and keep saving disabled. Older music documents containing unexpected release fields are rejected rather than silently discarding them.

Each release entry contains immutable `record` data plus `allowRemix` and `permissionRevision`. Release IDs identify v1 snapshots; another release receives another ID. The persistent request index prevents a retried release request from making another record. There are eight release slots, alongside the existing sixteen Finished Songs. Existing 1.2 MB project, 2.8 MB music and 3 MB full-profile limits are unchanged; no content is evicted to make room. Archive limits remain unchanged.

Creation and permission updates stage a complete music override and use `ProfileStore.save` through the existing service callback. Live library admission happens only after acknowledgement. Normal edits made during storage I/O remain live and dirty; callbacks update only the release entry/receipt and do not reinstall an older project. Workspace replacement remains blocked during saving. Restore/recovery use the existing workspace transaction and retain the current release library.

The existing DataStore name and revision-checked UpdateAsync backend remain unchanged. No production profile was accessed here. Future authorized deployment must coordinate/drain old writers and use compatible readers; do not run an older schema-3 client/server build against upgraded profiles. The version guard is data protection, not deployment authorization. Studio saves remain session-only. Storage acknowledgement can be displayed only after the existing backend accepts a snapshot; actual hosted leave/rejoin and conflict behavior is not established by this batch.
